# Internal implementation security review

This is a source-level review and regression-test record from the implementation team. It is **not an independent security audit**, penetration test, assurance certification, or approval for mainnet delegation. Review scope: authentication and tenant checks, versioned records, payment review/preparation, database constraints, document storage, API boundaries, deterministic domain controls and the new Solidity contracts.

## Corrections made

| Finding | Correction and boundary |
|---|---|
| A payment review received full configured allowances instead of remaining capacity | Review subtracts settled expenditure and every unresolved allocation from lifetime capacity. Exact last-24-hour source expenditure plus all pending/uncertain allocations consume rolling capacity. Unknown legacy settlement timestamps remain conservative. Previous policy versions do not reset accounting. |
| Different engagements could race against the same policy budget | A shared organization transaction lock precedes engagement/invoice locks and allocation queries. Preparing a payment and inserting its durable allocation occur in one caller-owned transaction. An explicit engagement lock protects obligation allocation. This intentionally serializes treasury writes for correctness. |
| A changed invoice date range created a fresh obligation key | Intake persists obligation identity. Exact billing periods share an identity; differently bounded overlapping invoice periods produce an explicit hold. Editing an existing billing period cannot silently move that identity. This is an ambiguity hold, not a fraud finding. |
| Review silently applied the latest engagement version to an older invoice | Intake pins engagement and destination versions. Review compares those recorded versions with approved current terms. Reusing acceptance after an invoice version change is rejected. A newly reviewed correction is required where the terms no longer match. |
| Vendor address protection did not protect a chain-only change | Generic vendor writes reject changes to either address or chain. Safe identities also cannot be reassigned in place. |
| Destination changes lacked a usable authenticated workflow | Owner proposal and distinct owner/approver confirmation bind the exact vendor version and new destination. Both verify a current database session created within five minutes. A solo exception is visible, requires an explicit reason, proves there is only one eligible workspace member, and requires a second fresh wallet sign-in after the proposal. No browser-supplied `reauthenticated` flag is trusted. |
| A caller could reuse an idempotency key for a different invoice | Existing keys are bound to the original invoice; a different invoice is rejected. Revalidation may exclude only the current intent for the same invoice and engagement, preserving every other allocation. |
| `failed` could silently free uncertain capacity | Failure releases capacity only with recorded terminal nonexecution proof and no source transaction. An ambiguous failure or source-confirmed operation retains capacity. Provider errors are not such proof. |
| A Safe synchronization could be confused with complete history | Bounded chain observations remain incomplete. Owner reconciliation requires tenant-owned supporting documents and exact classification of every observed outgoing transfer. External invoice payments create stable, idempotent observed allocations; unknown transfers keep payment review on hold. Prior-history completeness still depends on the owner's source statements and attestation. |
| Invoice currency was silently coerced to USDC | Invoice and engagement currencies remain explicit. A USD-denominated invoice is not automatically treated as USDC settlement; missing approved conversion remains a hold. |
| Paused delegation also blocked manual preparation | Prepare mode can produce a non-executable human proposal with valid terms, limits and reconciled history. Live Delegate/unpause requires a manifest bound to the exact organization/Safe/chain plus current deployment-bytecode and recorded compatibility/recovery evidence. An environment flag alone does not satisfy this gate. |

Destination, policy and engagement changes mark safe unsubmitted intents invalidated. The worker must reject invalidated authorizations before new submission and atomically check invalidation in its submission state transition. Submitted, uncertain and source-confirmed payments retain their original identity and must continue reconciliation. **A database invalidation does not revoke an already signed on-chain permit.** Safe owners must pause/revoke or change the on-chain policy epoch when immediate revocation is required; otherwise the prior permit remains subject to its original expiry and on-chain bounds. Capacity is not released merely because an application flag changed.

`confirmHistoryReconciliation` checks exact observed transfer membership, duplicate log identifiers, tenant document access and recipient/chain/payment matches. It does not establish whether an uploaded statement is truthful, whether a non-payable classification is appropriate, or whether the owner omitted information from earlier history. It records the authenticated human's statement and supporting evidence rather than marketing a boolean as a verified fact. An external transfer matched to an invoice prevents allocating that same paid obligation again; it is never counted as a Countersign-originated transfer.

## Regression coverage

`tests/server/security-review.test.ts` runs against actual PGlite PostgreSQL storage with both migrations. It covers policy remaining capacity, old pending allocations, source-time rolling windows, ambiguous failed operations, stale invoice/engagement versions, overlapping periods, idempotency binding, current-operation exclusion, explicit currency, tenant and role checks, proposal expiry, fresh two-person/solo destination controls, concurrent preparation across engagements, and exact history matching/idempotent external allocation. Existing authorization and storage tests remain part of verification.

The contract suite separately tests all permit-field binding, caller/signer separation, EIP-1271 verification, replay/installment/obligation limits, midnight rolling-window bursts, policy changes, independent Safe administration, cash floors, collateral exhaustion, claimed-liability retention, payout recovery deduction, and restricted CCTP call/rollback behavior. Stateful invariants verify payment-effect accounting and reserve conservation. Local mocks are not evidence of compatibility with a specific deployed Safe or Circle wallet.

## Residual release requirements

1. Independently review the application, verifier, contracts, deployment composition and operational key policy before broad real-money delegation. Resolve critical findings and retain the reviewed commit and deployment manifest.
2. Prove the real Circle agent wallet/module call path and revocation behavior. Successful transaction hashes and code hashes are evidence references; their semantic interpretation requires review. No operator EOA substitution is permitted while claiming Circle-backed execution.
3. Validate actual source/destination token deployments, decimals, finality and fee behavior. The CCTP contract's amount is the gross source debit; recipient delivery and invoice reconciliation must use actual net delivery. Source burn alone is not a paid invoice.
4. Protect verifier and Circle credentials separately; production signer isolation and customer-specific credential administration remain operational requirements. A compromised verifier plus available executor authority can issue false business attestations within owner-installed limits.
5. Protect database credentials. RLS is enabled and no public data policies are granted; server code uses tenant predicates. The server/database-owner role is privileged and can bypass RLS, so SQL authorization is a critical application boundary, not a substitute for least-privilege deployment.
6. Supply encrypted-document key backup/rotation and recovery procedures. Documents use AES-GCM with organization-bound associated data and randomized commitments. Losing the encryption key loses document availability. Uploaded evidence remains untrusted; authentication does not prove document truth.
7. Provision independent reserve reviewer authority, accepted terms, adequate funding and a reviewer recovery procedure before advertising protection. Contracts have no unilateral operator escape that can impair open liabilities. Final claim resolution is final on-chain; an appeal process must precede that final action.
8. Preserve independent Safe owner access. The module cannot prevent owners/other modules from making outside transfers, cannot protect invisible liabilities or native gas costs, and cannot reverse completed payments. Application outages must not lock human treasury control.

The API review also identified deployment-facing input-resource and spreadsheet-export concerns: request bodies should be bounded while streaming, document uploads must fit the host's request limit, CSV formula defenses must include leading control/whitespace prefixes, and sign-in challenge issuance should have an additional abuse budget beyond the claimed wallet address. These belong to API/deployment verification; do not assume host defaults resolve them without testing.

Run `npm test -- tests/server/security-review.test.ts` and the complete repository verification command before release. This report describes implementation controls and remaining responsibilities; it is not a claim of audited safety or genuine customer usage.
